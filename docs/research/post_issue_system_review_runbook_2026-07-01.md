# Post-Issue System Review Runbook

Date: 2026-07-01

Use this after the current issue fully settles. The goal is to review the whole
decision chain, not just whether the final tickets won.

## Inputs To Freeze

Before settlement review, keep these snapshots separate:

1. Issue match list and final Beidan handicap.
2. Pre-match model probabilities after handicap calibration.
3. q / expected return for each result.
4. Recommendation and coverage depth per leg.
5. Ticket pool generated by the main strategy.
6. Any paper arms: stable baseline, convex baseline, tag paper arms, and
   manually observed LLM decisions.
7. Final score, half-time score, result code, and settlement SP.

## Review Sections

### 1. Issue-Level Outcome

- Total stake, payout, net profit, ROI.
- Whether the issue was full-loss, partial-loss, small win, or convex win.
- Current drawdown state after settlement.
- Whether this issue would have triggered any risk-state change.

### 2. Ticket Distance

For every selected ticket:

- hit / miss,
- missed by 1, 2, 3+ legs,
- which leg caused the miss,
- whether the missed leg had a known tag: `prob_guard`, `draw_guard`,
  `full_watch`, `q_prob_divergence`, `deep_fav_oppose`, or
  `model_market_conflict`,
- whether a nearby swap ticket would have hit.

The most important output is not the hit ticket itself, but repeated near-miss
patterns that can be turned into depth rules.

### 3. Leg-Level Decision Review

For each leg:

| field | review question |
| --- | --- |
| model probability | did the probability model rank the actual result reasonably? |
| q / EV | was the selected result high EV or only high SP? |
| Beidan handicap | did the handicap create a misleading forced direction? |
| SP / settlement SP | did final settlement SP support or punish the selection? |
| LLM judgment | did contextual reasoning agree with model/q or flag a conflict? |
| coverage depth | should this have been single, double, full, or skipped? |

### 4. Strategy Arm Comparison

Compare at least these arms for the issue:

- `current_reference_256`
- `b384_dd32_smooth100`
- `b384_dd32_smooth80_convex19`
- `tag384_dd32_smooth76_tag19_prob_guard_t4_l3`
- `tag384_dd32_tag76_convex19_full_watch_t1_l1` as paper convex only

Record:

- issue profit,
- tickets used,
- hit tickets,
- missed-by distribution,
- whether the arm improved survival or only increased convexity.

### 5. Decision-Chain Update

Only update the strategy when the issue reveals a repeatable rule. One issue can
create a hypothesis, not a production rule.

Possible rule updates:

- add a leg tag,
- adjust depth for a tag,
- cap issue concentration,
- change LLM prompt/checklist,
- change display priority in Match Detail,
- create a paper arm.

Avoid updating:

- global q thresholds from one issue,
- SP drift gates based on one settlement,
- full-cover behavior from one rescued ticket.

## Output Format

Create one markdown report under `docs/research/`:

`post_issue_review_<issue>_<YYYY-MM-DD>.md`

Minimum sections:

1. Summary verdict.
2. Issue-level PnL.
3. Ticket distance table.
4. Leg-level misses.
5. Arm comparison.
6. What the LLM got right/wrong.
7. Action items for strategy/frontend/data.

## Current Working Hypothesis

The strategy should be reviewed through this frame:

- Use probability and context to select the main result.
- Use q / SP to decide whether the payoff is worth trading.
- Use tag-derived uncertainty to decide coverage depth.
- Use high-convexity `full_watch` only as capped paper or small sleeve until it
  proves it can avoid unacceptable maxDD.
